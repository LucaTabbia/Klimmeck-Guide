# Review rulings — Phase 17 Unlockable Lore (orchestrator, 2026-11-07)

Facts checked on the code before ruling: `MainScreenCubit.refreshCities()` (`main_screen_cubit.dart:29-40`) has no in-flight guard: two calls overlap, each awaits its own `getCities()` and emits whatever arrives last; a call made while `loadData()` is still in `MainScreenLoading` returns at line 30 and is never replayed. `LibraryCubit.syncUnlockedLore()` records `_lastUnlocked` and returns at line 66 while `openBook` is in `LibraryLoading`, so a set change that lands during the opening fetch is only applied at the next change. `LibraryErrorPage` (`library_error_page.dart:8`) is still Flutter's debug `Placeholder`, reachable from `library.dart:57-58` on any failed `openBook` (a normal book tap), with no way back (`LibraryError.errorMessage` is never rendered — and must not be rendered raw). `strongestEnemyOf` (`quest_enemy.dart:131`) has no caller in `lib/` after 17-04 (only `quest_enemy_test.dart:215-264`). The «unlocked set changed» test exists twice by design (the Library cubit compares against its own `_lastUnlocked` because it must record the first set and ignore changes while no book is open; the Map listener compares two states), but the `status?.unlockedLore ?? const []` extraction is duplicated in `main_screen.dart:104-110` and `library.dart` (`_unlockedLoreOf`). The baseline writes (IN-02) are dispatched in call order: `openBook` starts `_writeBaseline` synchronously right after its emit (line 56), before any live refresh can run, and both writes go through the same `SharedPreferencesAsync` platform channel, which preserves order; the worst case is a cosmetic extra «Nuovo».
