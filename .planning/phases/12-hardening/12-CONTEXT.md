<domain>
## Phase Boundary

Close v1.0 with an intensive pass on bugs, security and concurrency so the shipped app survives real users and real streams without leaking state, double-refreshing or breaking under multi-device pressure. Concretely: the production entry point carries no dev bypass and no `.env`, the release build is signed with the user's keystore, talks only TLS and logs nothing; the session layer is proven end to end (atomic logout, single-flight refresh, no retained subscriptions or cubits after logout, with a leak-tracking test and a DevTools snapshot); the same Twitch account logging in on a second device replaces the first one cleanly («l'ultimo login caccia l'altro», a BE Phase 17 rule) with a specific sign-in notice, and every identity transition rebuilds the whole shell; the follow-ups parked here since Phases 8, 10 and 13 are closed; a cross-cutting review by area fixes what it finds; a GitHub Actions pipeline guards all of it on every PR.

Out of scope: new gameplay or UI capabilities, the heal mechanics of `canHeal` (its own future phase, quick tasks 261109-inj/inj2), «esci da tutti i dispositivi» (BE backlog), a diagnostics badge for the WS connection (rejected in Phase 3 D-17 and again here), per-request session lookups on the BE (the JWT stays stateless), iOS release work (Android only in v1.0), store listing and publication, the accessibility pass (FUT-04).

## Implementation Decisions

### Dev bypass, `.env` and the release build (criterion 6, HARDEN-01, HARDEN-07, HARDEN-08)
- **D-01 (user decision, «Entry point separato»):** the dev bypass moves to a dedicated entry point **`lib/main_dev.dart`**, which composes `DevAuthTokenService`, loads `.env` through `flutter_dotenv` and keeps today's dev behaviour (D-23..D-30 of Phase 11: `DEV_AUTH_*` knobs, instant login, `DEV_AUTH_START_SIGNED_OUT`). **`lib/main.dart` becomes production-pure**: no `DevAuthTokenService`, no `DEV_AUTH_*`, no `flutter_dotenv` import; `_buildAuth` composes only `SessionAuthTokenService`. The two entry points share one composition module (no duplicated wiring: the dev file only swaps the auth factory). Device UATs run with `flutter run -t lib/main_dev.dart`; the gate is a grep that proves `lib/main.dart` and the release bundle contain neither `DevAuthTokenService` nor the string `DEV_AUTH_`. **Revised after the research (F1, Pitfall 4):** the barrel `lib/repository/services/auth/auth.dart:7` re-exports the dev service and must drop that export (no test needs it through the barrel); `KlimmeckGuideApp` and `navigatorKey` move from `main.dart` to `lib/bootstrap/klimmeck_guide_app.dart` so `lib/main.dart` becomes `Future<void> main() => bootstrapApp(buildAuth: buildSessionAuthComposition);`; `lib/bootstrap/auth_composition.dart` holds the typedefs `AuthComposition` / `AuthCompositionFactory`; `bootstrapApp({required AuthCompositionFactory buildAuth, bool isRelease = kReleaseMode})` builds the `GraphQlBackendAuthApi` and runs the TLS gate first; `buildDevAuthComposition` falls back to the session composition when `DEV_AUTH_ENABLED` is not `true`; `lib/main_dev.dart` asserts `appFlavor == 'dev'` first, then `dotenv.load` → `EnvConfig.installRuntimeOverrides(dotenv.env)` → `bootstrapApp(buildAuth: buildDevAuthComposition)`.
- **D-02 (user decision, «Niente .env in release»):** the release build ships **no `.env`**. Backend URLs come from **`--dart-define-from-file=env/<ambiente>.json`** (URLs only, no secret: the file can live in the repo; `EnvConfig` already reads `String.fromEnvironment` as the second priority). `.env` + `flutter_dotenv` stay a convenience of the dev entry point only. Mechanism to keep the asset out of the release bundle (pubspec asset `flavors:` with a `dev` flavor, a build-time copy, or another verified option) is **researcher/planner discretion**; the truth is the gate: the built release APK contains no `.env` entry and no `DEV_AUTH_` string. **Revised after the research (F2, probes P-B0..P-B8, C-1, C-2, C-3, Pitfall 1, 2, 12):** the mechanism is the **asset flavor**: `pubspec.yaml` lists `- path: .env` with `flavors: [dev]`, `android/app/build.gradle.kts` adds `flavorDimensions += "env"` and `productFlavors` `dev` / `prod` with the same `applicationId`, and `pubspec.yaml` sets `default-flavor: prod` in the same commit (without it every unflavored build fails). Consequences: the dev run becomes **`flutter run --flavor dev -t lib/main_dev.dart`**; `flutter build apk --release --dart-define-from-file=env/prod.json` builds `prodRelease` → **`build/app/outputs/flutter-apk/app-prod-release.apk`**, also with no `.env` on disk (the CI case: today a checkout without `.env` fails the build). The bundle gate is **`unzip -l <apk> | grep -c 'flutter_assets/\.env$'` = 0, `unzip -p <apk> | grep -a -c DEV_AUTH_` = 0, `unzip -p <apk> | grep -a -c DevAuthTokenService` = 0** (a raw `grep -a` on the APK misses deflated entries; the manifest grep is always 0); `flutter_dotenv` is gated in the **source** (`lib/main.dart`, `lib/bootstrap/app_bootstrap.dart`, `lib/config/env_config.dart`), because `EnvConfig` imports it today and the seam `installRuntimeOverrides` / `resetRuntimeOverrides` is what removes it from the prod binary (probe P-B7). `env/prod.json` holds **RFC 2606 placeholders** (`https://api.klimmeck.invalid/`, `https://api.klimmeck.invalid/api/graphql`, `wss://api.klimmeck.invalid/api/graphql`: TLS-valid shape, compiles in CI, unreachable) until a production host exists; the UAT uses a gitignored **`env/tunnel.local.json`** (pattern `env/*.local.json`). `env/*.json` never carry `DEV_AUTH_*` keys.
- **D-03 (user decision, «Tutto in scope»):** release readiness is part of this phase: (a) **signing** — the release build reads the keystore from **`android/key.properties`** (already in `.gitignore` with `*.jks`); **the user generates the keystore and the properties file** (exact `keytool` command and the four keys documented in the handoff); when the file is missing the build **falls back to the debug keys with a visible warning**, so CI and `flutter run --release` keep working; (b) **TLS only** — in release the app refuses cleartext `http://` / `ws://` backend URLs (fail fast at startup with a clear, non-gameplay screen; copy and shape Claude's discretion), closing AR-03 of the Phase 3 security audit; `EnvConfig.isDebug` / `enableLogging` default to `false` in release; (c) **no logging in release** — `debugPrint` calls are routed through one logger that is silent under `kReleaseMode` (or stripped), and the token-hygiene grep proves no token or bearer value ever reaches a log statement. **Revised after the research (F3, F4, F5, probes P-S1..P-S3, Pitfall 3):** (a) the Kotlin DSL reads `rootProject.file("key.properties")` into `Properties`, creates the `release` signing config only when the file exists, otherwise falls back to `debug` with **`logger.quiet("WARNING: android/key.properties not found: the release build is signed with the DEBUG keys and cannot be published.")`** (`logger.warn` is swallowed by the `-q` the Flutter tool passes to Gradle); `storeFile` must be an **absolute path** (a relative one resolves from `android/app/`); signature verified with `apksigner verify --print-certs` from build-tools 36.1.0 with `JAVA_HOME` = the Android Studio JBR (no system Java on this Mac); handoff `keytool` command through the JBR, alias `upload`, `storePassword` = `keyPassword`; (b) `EnvConfig.requireSecureTransport({bool isRelease = kReleaseMode})` runs **first** in `bootstrapApp`, before push and before any client is built, checks `baseUrl`, `graphqlHttpUrl`, `graphqlWsUrl` for `https` / `wss` and throws `InsecureTransportError(List<String> offendingKeys)` in release (dart:io ignores Android's cleartext policy, so the refusal must be Dart-side); in debug/profile it only logs; both branches tested through `isRelease` and the overrides seam; the built-in `http://192.168.0.20` defaults stay (a release built without the dart-define file fails fast instead of talking cleartext); `InsecureTransportScreen` is a minimal `MaterialApp` with a centred text, no button, no network; (c) **57 log call sites in 28 files** (53 `debugPrint`, 3 `print`, 1 `developer.log`), none interpolates a credential; `lib/utils/app_log.dart` exposes `appLog(String)` = `appLogWith(message, isRelease: kReleaseMode, sink: debugPrint)` (pure, testable on both branches); every call is routed through it (Boy Scout: `$e` → `${e.runtimeType}` where an exception is logged); `isDebug` / `enableLogging` default to `!kReleaseMode` (no reader outside `env_config.dart`).
- **D-04 (user decision, «Tunnel TLS verso il BE locale»):** the release build is exercised on the device through a **TLS tunnel to the local BE** (`cloudflared tunnel` or `ngrok`), with `--dart-define-from-file` pointed at the tunnel host; the real Twitch login runs through it. Prerequisite for the user: the tunnel's public URL must be an allowed redirect URI of the Twitch application (or a stable named tunnel is used), written in the UAT sheet. Nothing new is deployed. **Revised after the research (F13):** the login chain opens `EnvConfig.baseUrl` + `auth/twitch/start` in the system browser, the BE redirects to Twitch with its own `TWITCH_REDIRECT_URI`, the BE callback ends on the deep link `klimmeck://auth` (host-independent): for the release UAT the BE `.env` gets `TWITCH_REDIRECT_URI=https://<tunnel-host>/auth/twitch/callback`, the same URL is added to the Twitch application's OAuth redirect URLs, the BE is restarted; a **named tunnel** (stable host) is preferred over a quick tunnel; `cloudflared` and `ngrok` are not installed (`brew install cloudflared` is a user prerequisite); the BE throttler keys by IP and sees both devices behind the tunnel (note in the sheet); the BE needs no code change (BE Phase 17 D-16).

### Multi-device and identity transitions (HARDEN-06, HARDEN-02 evidence)
- **D-09 (user decision, «L'ultimo login caccia l'altro», BE Phase 17 D-02/D-03/D-04):** a login on a second device **revokes the other sessions of the user on the BE**, which **closes their WebSocket connections at once** with a dedicated close code; the access JWT of the replaced device stays valid until its natural expiry (15 min, stateless, no per-request lookup). On the FE the replaced device reacts to the close as it does to `4401` today (refresh before reconnect, Phase 11 D-07/D-37): the refresh is refused with `SESSION_REVOKED` + `reason`, the session is torn down (same path as a revocation, D-09 of Phase 11) and the sign-in screen shows the **specific notice** (D-12). Bounded reconnects, no hot loop, no blocking UI (rule 2). **Revised after the research (F7):** the close reason of `4409` is not parsed (the refused refresh is authoritative); `WsReconnectPolicy.onConnectionLost` routes `4409` like `4401` into `recoverFromUnauthorized(rejectedToken: _lastSentToken)` → single-flight refresh → `SessionRejected` with the reason; if a rotation raced the close, the reconnect hits `4409` again at `connection_init` and the next round refreshes (converges); `_endSession` → `GraphQLClientHolder.reset()` disposes the link, so no reconnect loop follows the revocation.
- **D-10 (user decision, «Solo quel device»):** logout keeps closing **only the current session** (Phase 11 D-12 step 1); the other device stays logged in. «Esci da tutti i dispositivi» stays in the BE backlog (deferred).
- **D-11 (user decision, «Reset totale della shell»):** identity transitions rebuild the whole shell by construction — **already the design**: `AuthGate` keys the authenticated subtree on `user.id` and `SessionHome` on `character:<id>`, root-Navigator dialogs and sheets are closed on both changes (Phase 3 D-10, Phase 11 D-26). This phase **proves it** with tests (account switch on the same device; character deleted or recreated from the other device → creation screen, then a fresh shell for the new id) and fixes any gap found (a cubit or listener surviving the key change, a push intent routed to a stale character). No «refetch in place» variant. **Revised after the research (F8):** above the `user.id` key live only process-wide or stateless objects (`AppLifecycleBridge`, the GraphQL/REST facades, the stores keyed per call, `PushRegistrationCoordinator` which already handles a user change, `NotificationIntentCubit`, `NotificationTapRouter`, `AuthCubit`, `SplashCubit`); one gap candidate for the reviewers of D-14: `NotificationIntentCubit` keeps a pending tap across a direct `Authenticated(A) → Authenticated(B)` (clear it when `previous.user.id != next.user.id`, with a test); existing coverage `auth_gate_test.dart:190,207,248,303-405`, `session_home_test.dart:100,119,183,201`; the missing cross-device sequence goes in **`test/screens/auth/identity_transitions_test.dart`** (`SessionSyncScope` + `AuthGate` + `SessionHome` over a fake `AuthTokenService` whose `adoptUser` re-emits `AuthAuthenticated`, a `StreamController` behind `subscribeToUser`: `currentCharacter: null` → creation page with a fresh cubit → new character id → new shell, previous cubits closed, root dialogs closed).
- **D-12 (user decision, «Specifico quando il BE lo dice», BE Phase 17 D-05):** the refresh refusal keeps the code `SESSION_REVOKED` and adds **`extensions.reason`** (enum, names fixed in the BE `17-REPO-RULES.md`; technical defaults `newLogin`, `roleChanged`, `reuseDetected`, `userLogout`); the same string travels in the reason of the dedicated WS close. The FE parses it **leniently** (unknown or missing → the neutral Phase 11 D-10 notice «La sessione è scaduta, accedi di nuovo.») and shows dedicated copy for **`newLogin`** («Hai effettuato l'accesso da un altro dispositivo.», copy Claude's discretion) and **`roleChanged`** («Il tuo ruolo è cambiato, accedi di nuovo.»). Implementation: new `UnauthenticatedReason` and `SignInNotice` values; `SessionRejected` carries the reason. Gated plan (BE contract). **Revised after the research (F7, Pitfall 8):** `mapAuthOperationException` parses `extensions.reason` from the **same** GraphQL error that carried the code and honours it **only when `code == SESSION_REVOKED`**; `SessionRejected(this.code, {this.reason})` with `reason` in `props` (null-reason equality keeps the existing tests green); `_rotateSession` maps `newLogin` → `replacedByNewLogin`, `roleChanged` → `roleChanged`, anything else or null → `sessionExpired`; cold start and proactive refresh share `_rotateSession`, so an offline revoked device gets the notice too; `handleRevocation()` stays `sessionExpired`; the logout-only refresh ignores reasons (logout wins); `AuthGate._noticeFor` is an exhaustive switch (the new enum values are a compile error until mapped); `_shouldRebuild` already rebuilds on a reason change.
