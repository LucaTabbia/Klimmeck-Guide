<objective>
Wiring tra `AuthTokenService` e gli strati di network: (a) `GraphqlClientProvider` usa `AuthLink` + `WebSocketLink.initialPayload` per iniettare il token a ogni richiesta, (b) espone `recreate()` che dispose+ricostruisce il client (D-12 step 3), (c) un `AuthDioInterceptor` gestisce 401→refresh→retry su REST, (d) il callback `onLogoutCompleted` di `AuthTokenService` invoca `recreate()` chiudendo il ciclo di logout teardown.

Output: GraphQL client e dio autenticato pronti per essere forniti via `RepositoryProvider` nel plan 05.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → backend (HTTP + WS) | Il token in Authorization header è la credenziale |
| logout → subsequent session | Tra una sessione e l'altra non deve rimanere alcuno stato network/listener |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03-01 | Information Disclosure | Stale subscription dopo logout (account bleed) | mitigate | `GraphqlClientProvider.recreate()` dispose+ricrea `WebSocketLink` + `GraphQLCache`; callback invocato in step 3 di `AuthTokenService.logout` (wiring in plan 05) |
| T-01-03-02 | Spoofing | WebSocket non aggiornato dopo token refresh (pitfall #4) | mitigate | `initialPayload` è `Future<Map>` async: legge sempre il token corrente da `authService.getAccessToken()`. In-session refresh: il WS si riconnette automaticamente (`autoReconnect: true`) e il nuovo `connection_init` usa il token fresco (rivalutare con BE team — open question #1) |
| T-01-03-03 | Denial of Service | Loop di retry 401 infinito | mitigate | Flag `auth_retry` in `RequestOptions.extra` limita il retry a 1 |
| T-01-03-04 | Elevation of Privilege | Twitch OAuth endpoint riceve il Bearer dell'API di gioco | mitigate | Interceptor esclude `id.twitch.tv` dall'attaching del Bearer |
</threat_model>
